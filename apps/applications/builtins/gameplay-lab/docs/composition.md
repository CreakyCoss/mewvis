# 玩法组合与模块接入

游戏沙盘将玩法分成骨架、可选模块、布局模板和经典预设。预设是一份经过验证的组合配置；用户修改同一份配置形成自定义方案，编辑、执行、牌桌与回放都使用相同的装配流程。

当前完整接入斗地主与组合计分两套骨架。斗地主提供经典、英雄预设，组合计分提供基础、配对计分预设；自定义方案使用同一装配流程。资源发展和分支叙事保留已有入口。模块只在声明兼容的骨架内装配。

## 职责

| 层次     | 负责什么                                                 | 斗地主实例                         |
| -------- | -------------------------------------------------------- | ---------------------------------- |
| 骨架     | 完整推进流程、基础状态、合法操作、玩家信息边界和胜负     | 发牌、叫分、跟牌、过牌、阵营结算   |
| 模块     | 配置、校验、运行状态、命令、玩家视图、自动决策与界面贡献 | 英雄洞察                           |
| 布局模板 | 基础游戏场景及模块可使用的区域                           | 三人牌桌，提供手牌前区域与对手区域 |
| 经典预设 | 骨架、规则、模块与布局的初始组合                         | 经典斗地主、英雄斗地主             |

骨架不直接导入某个英雄模块的编辑器或执行逻辑。可选能力由注册表接入；模块关闭后，不参与状态初始化、命令候选、自动决策、编辑导航和牌桌渲染。

## 项目描述

创建页通过 `frameworks/creation.ts` 读取框架的预设与创建方式，不在表单中判断具体框架。斗地主可以选择经典或英雄斗地主，组合计分可以选择基础或配对计分。在“玩法组合”中增减兼容模块，在“牌型与结算”和动态出现的模块页面中编辑内容。更改参数后，方案标记为自定义组合；不需要切换另一套运行器。

模型中的组合示例：

```json
{
  "composition": {
    "version": 1,
    "skeleton": { "id": "doudizhu", "version": 1 },
    "layout": { "id": "three-player-table", "version": 1 },
    "modules": [{ "id": "heroes", "version": 1 }]
  }
}
```

各模块的具体内容保存在 `extensions[模块标识]`，包含模块版本和启用开关。组合引用、配置版本与开关必须一致，模块管理操作会一起更新它们。关闭模块保留内容。应用预设会先要求确认，页面明确说明该框架会替换哪些设置；斗地主恢复预设规则与启用模块默认内容，组合计分只切换模块并保留卡牌、牌库和奖励数值。已保存版本和历史对局不受影响。

## 通用装配契约

`main/frameworks/composition/` 提供不依赖具体玩法的契约、解析器、运行装配器和界面装配工具。

- `SkeletonDefinition` 声明版本、能力、允许的时机、基础命令和保留状态字段。
- `LayoutDefinition` 声明支持的骨架与区域。
- `ModuleRuntime` 声明模块版本、兼容骨架、依赖能力、模块依赖、时机、区域，以及配置和运行回调。
- `ModulePresentation` 提供编辑组件与各区域的游戏组件。确定性执行不依赖 React。
- `GameComposition` 引用选定骨架、布局与模块版本。

解析器先校验配置和引用，再按依赖顺序排列模块，同级保持配置顺序。未知版本、缺失依赖、依赖循环、不支持的时机或区域、命令重复和状态字段冲突均阻止运行，不会静默忽略。

运行装配器统一处理初始化、视图、命令和自动决策。模块命令必须属于声明的命令类型，并与当前玩家视图中的合法候选一致；骨架继续约束行动玩家、结束状态和步数上限。每个模块独立持有自己的状态字段。正常玩家视图先剥离所有模块内部状态，再由启用模块分别提供公开或属于该玩家的信息，不能直接展开模块内部状态。

模块可以通过 `projectRules` 在 `rule-compile` 时机贡献实际执行规则。装配器在副本上编译规则，冻结模型仍保存用户原始配置；预估和自动决策读取同一份有效规则。模块命令按记录顺序执行，单条命令只有一个模块负责；当前没有共享事件总线或自动连锁触发系统。`before-play` 表示自己的出牌决策窗口，新增其他时机需要骨架明确提供对应语义。

## 接入一个模块

1. 在所属框架的模块目录提供配置及校验、运行实现和配套界面。
2. 实现 `ModuleRuntime`，声明依赖、时机、状态字段与命令所有权；自动决策只读取玩家视图。
3. 实现 `ModulePresentation`，提供编辑器和布局区域组件。
4. 在框架的运行与界面注册表登记模块，两套卡牌骨架都通过自身的 `composition/catalog.ts` 和 `composition/ui.tsx` 接入。项目创建能力与预设在 `frameworks/creation.ts` 登记。
5. 如有经典组合，在预设中引用模块标识；无须给工作区、斗地主核心执行器或基础牌桌逐处添加该模块的条件分支。
6. 验证合法操作、信息隔离、模块关闭、组合依赖、保存恢复和冻结回放。

斗地主的 TypeScript 开放接口允许模块在自己的注册文件中扩展配置、命令、事件、状态和玩家视图类型；骨架与工作区保留公共契约。

## 冻结与重算

新对局同时冻结模型配置和解析后的骨架、模块、布局版本。组合计分在 `RunLog` 中保存组合与模块状态，试玩记录和实验样本均按相同信息重算。重算先校验组合，再使用同一装配器重放命令；修改草稿或应用其他预设不改变旧局。

原有未记录 `composition` 的 v1 项目和对局按已有配置在内存中解析组合，读取不会补写或转换磁盘文件。新格式记录缺少组合快照，或快照与冻结模型不一致时会拒绝加载并保留原文件。

测试还会将一个仅用于测试的独立模块注册到真实斗地主核心，验证它能与英雄模块共同初始化、运行和隔离视图；该模块不作为产品玩法提供。

## 组合计分的配对奖励

配对奖励是 `card-scoring` 骨架的兼容模块，贡献规则编译、奖励编辑页和牌桌公式区域。基础计分骨架按零配对奖励执行；启用模块后恢复每个计分行动中配置的奖励金额。金额仍保存在原有 `combination.pairBonus` 字段，模块配置保存版本与启用状态，避免重复保存两套金额。

关闭模块会一起改变预估得分、自动玩家选牌和实际结算，但保留奖励参数。启用项变化不会改写已开始的对局。该模块随正常出牌计算，不产生独立玩家命令。

组合计分玩家视图隐藏抽牌顺序及其他玩家的手牌，保留公开张数；自动决策使用相同的信息边界。独立检查面板可主动展开完整牌区。

## 已确认的共享能力

两种骨架复用 `domains/card/primitives.ts` 中的整数随机序列、确定性洗牌与实体牌选择校验，保留各自的种子初始化和牌实例定义。叫分、跟牌、阵营结算与数值计分、抽补牌仍分别由各自骨架处理。组合管理页面也通过 `CompositionDesign` 共用，不复制框架专用表单。
