# 游戏沙盘：按类型策划与玩法原型验证

日期：2026-10-29。此规划替代此前“通用策略模型 → 不同玩法模拟器”的扩展方式。类型化基础、最小叙事闭环及独立卡牌模型已落地；跨关卡构筑、棋盘经济和塔防尚未实现。

## 产品目标与边界

用户选择游戏类型和玩法框架，从空白定义自己的游戏内容与规则，在明确支持的范围内人工试玩或进行自动验证。示例是可选初始内容。用户设计的内容称“策划方案/玩法规则”，自动玩家的决策逻辑称“策略”。

类型是组织入口，不承诺同一类型内所有游戏共用完整模型。玩法框架确定具体规则体系、编辑器、执行语义和验证范围。类型之间可以共用底层机制，但不把人物、剧情、卡牌、地图与防御塔都塞进一份通用表单。

设计目标还应表达期望的玩家体验和反复做出的选择。可执行性、数值表现和人工体验观察是不同的验证结论。

## 用户流程

```mermaid
flowchart LR
  A[选择游戏类型] --> B[选择玩法框架]
  B --> C[编写内容和规则]
  C --> D[兼容性及就绪检查]
  D --> E[人工试玩或类型适用的自动验证]
  E --> C
```

空白指没有预填内容，仍具有该类型需要的结构。创建界面选择确定的玩法框架，框架准备必要结构；试玩前补齐自己的内容与参数。方向和示例来源分别保存。

不同规则含义的转换应新建方案或实验变体，不能靠字段改名自动适配。类型切换不提供卡牌到剧情的自动转换。示例应用只在当前类型内提供，并沿用备份与确认流程。

## 分层结构

| 层次       | 责任                                                       |
| ---------- | ---------------------------------------------------------- |
| 平台       | 项目目录、读写、标识、引用、命名版本、快照、记录、实验管理 |
| 类型/机制  | 卡牌与牌区、剧情与条件、棋盘与资产、路径与单位等专门表达   |
| 玩法框架   | 明确的规则体系、支持机制、结算顺序、合法操作与结束方式     |
| 验证模拟器 | 实现所支持的方向，提供试玩界面、事件、回放与适用指标       |
| 示例       | 复制到用户项目的初始内容，不决定类型身份或运行行为         |

内部复用确定性执行、原子提交、序列化与文件服务；前台使用适合领域的名称和表单。不要先建设任意机制拼装框架。

当前 `main/frameworks/catalog.ts` 登记类型、方向、规则模型格式、验证模拟器及其版本和范围。一个方向目前对应一个内置模拟器。以后扩展到同一方向的多个实现时，必须检查规则语义一致；不支持将不同玩法作为同一个方案的皮肤切换。

## 当前已实现

| 游戏类型     | 玩法框架     | 编辑与执行范围                                                                                  | 尚不包含                                         |
| ------------ | ------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 卡牌         | 组合计分     | 卡牌定义、牌库数量、实体牌、牌区、开局抽牌、出牌上下限、可配置补牌与回收、组合计分及回合目标    | 战斗、通用触发链、完整牌型与构筑商店             |
| 回合资源经营 | 回合资源发展 | 资源、行动成本、周期产出、能力前置与阈值目标                                                    | 棋盘、地块归属、移动与租金                       |
| 文字冒险     | 条件分支叙事 | 人物、剧情节点、结局、布尔/整数/文本变量、全部满足的选项条件、赋值/加减后果、手动试玩与路径回放 | 自由输入对话、生成式人物行为、复杂任务和关系系统 |

卡牌使用独立 `gameplay-card-v1`，与经营复用数值规则及结算基础。卡牌定义、牌库构成和实体牌已分离，尚不提供任意触发体系或跨关卡构筑。叙事使用独立 `gameplay-narrative-v1`，不含资源行动、回合或数值达标目标，使用独立执行器和记录解析器。

数值玩法继续提供玩家策略、场景、版本对照与参数扫描。叙事提供结构可达性检查、人工试玩、当前条件与状态变化、死路与运行预算提示；不会套用通关率表格宣称剧情质量。结构可达性不穷举条件组合，不代表实际路径可达性。

## 兼容性约束

试玩前检查类型、方向、模型格式、模拟器标识与版本，以及具体规则引用与内容。运行时使用同一份冻结规则进行条件检查和结算，不能忽略不支持的效果或选项。

- 方向必须属于当前类型，模型格式必须匹配。
- 数值玩法的卡牌与资源能力由现有校验器检查；经营方向拒绝牌池与组合计分。
- 叙事条件和后果必须使用已存在且类型匹配的变量，目标剧情和发言人物有效；非结局节点需要选项，结局节点不能带被忽略的选项。
- 后果按顺序在副本上执行；越界或无效选择不留下部分状态。
- 记录冻结模型和执行器版本，读入时重算验证；不兼容格式与损坏记录保留原件并单独提示，用户确认后才可删除。

未知或不兼容的数据不能通过选中一个类型名称就获得执行能力。

## 当前主流程调整

采用完整玩法框架作为使用入口，具体结构、专属编辑和游戏场景由框架提供。用户在框架内设计内容并调整参数；高级规则与内容目录保留为辅助工具。[组合计分框架](frameworks.md)已提供必要结构、专属配置和独立牌桌，本轮不增加奖励、商店或跨关卡玩法。

## 后续实施顺序

### A. 类型化基础与异构验证（已完成）

1. 创建与项目库显示类型、方向、示例来源；只提供当前支持的方向。
2. 保留两类数值玩法，将卡牌编辑入口改为牌池与卡牌，经营入口保留流程与产出。
3. 新增独立叙事模型、人物/剧情/变量编辑器及人工执行器。
4. 叙事支持从零创建、保存重开、条件分支、状态后果、结局、版本与冻结记录回放。
5. 生产文件服务集成测试验证不同模型共存、外部变更保护及容量边界。

### B. 基础配置与编辑（当前优先级）

先完成应用基础与现有类型的编辑能力，详见[基础配置能力盘点](foundations.md)。本轮补齐内容目录、搜索与类型筛选、草稿引用检查及定位编辑、校验问题修复入口。仍需完善内容复制与排序、命名版本管理、编辑撤销/重做和跨验证配置的逐项定位。

这些能力服务于用户从空白内容开始策划，不要求增加默认预设，也不新增具体玩法规则。

### C. 深化卡牌的具体玩法框架（后续）

第一批已完成：独立卡牌定义与牌库数量、实体牌与牌区、开局抽牌、出牌上下限、补牌时机、弃牌回收，并接入编辑、校验、试玩、冻结记录、版本、数值实验与生产文件服务。内置卡牌示例直接使用当前模型；不保留旧执行路径或升级入口。不兼容数据只提示并保留，删除需用户查看范围后明确确认。

基础编辑完善后，再单独规划出牌计分 → 奖励/商店选择 → 构筑变化 → 下一关的闯关构筑方向。这属于具体玩法框架，不作为所有卡牌项目的必填配置。受控效果与触发顺序按这一闭环的实际需要增加，每个机制一起交付编辑、校验、执行、事件、回放与测试。

牌型、持续效果和构筑选择按实际需求增加。用少量用户自定内容验证系统，避免将开发重点放在扩充默认卡牌或复刻某个商业游戏。

### D. 扩展叙事及类型适用的验证

按真实案例增加条件组合、关系/物品/任务结构和路径测试；保留人工阅读试玩。条件可达性验证需要明确搜索边界，循环与巨大状态空间不能误报为完整覆盖。

### E. 棋盘经济与塔防

- 棋盘经济：棋盘、掷骰移动、地块触发、资产归属、购置、收租与破产；验证局长、先手、现金流与资产集中。
- 塔防：独立空间与时间推进、路径、建造、防御塔、目标选择、攻击与波次；验证漏怪、射程与位置、升级和波次压力。

两类目前在创建入口标为尚未提供，不能用当前数值模拟器冒充完整支持。混合类型与可复用机制组合在上述垂直闭环稳定后再扩展。

## 本轮验收证据

- 用界面从空白建立“港口来信”：自定人物、标记、剧情和两条选项；没有来信时不能启航，取得来信后到达结局。
- 保存重开、命名版本、历史回放验证；草稿改写结局后，旧记录仍保持原正文及状态变化。
- 回归两份已有示例的按类型创建、专属规则入口、自动玩家单步和文件记录。
- 桌面及窄屏验收证据位于 `output/gameplay-lab/typed-design-qa/`。原生目录选择器由隔离预览替代，真实宿主交互仍需在 Mewvis 中使用。

## 2026-10-29 具体玩法框架落地

应用通过框架登记进入工作区；组合计分页面和牌桌通过适配器接入数值工作区。斗地主具备独立模型和核心流程，并已接入通用组合契约、兼容性解析、运行与界面装配：经典预设和自定义方案共用入口，英雄模块通过注册提供配置、技能目标、私有结果、自动对手和冻结回放。其他框架尚未迁入组合协议，更多规则表达能力与专属批量验证仍待增加。
